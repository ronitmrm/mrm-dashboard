# Unified PostgreSQL migration

Date: 2026-07-18

The implementation contract is
`docs/postgresql-migration-spec.md`.

Durable decisions:

- `mrm-dashboard` is the target project and PostgreSQL is the sole target
  business database.
- Use PostgreSQL schemas to separate identity, catalog, sales, manufacturing,
  workforce, quality, maintenance, audit, derived state, and migration
  staging.
- Pricing has 42 final SQLite tables. Its startup `migrate()` function also
  performs repairs/backfills, so final extraction must use the pinned source
  version and a consistent SQLite backup.
- Convex has 12 canonical application sources plus auth and two disposable
  derived snapshot tables. Decompose `dataEntries` by logical type; never port
  it wholesale as a primary JSONB entity store.
- Use immutable source artifacts, checksums, staging, source ID maps,
  idempotent loaders, and explicit conflict queues.
- Use a rehearsed maintenance-window cutover with a write freeze. Do not build
  cross-database dual writes for the first migration.
- Keep a temporary versioned JSONB dashboard read model generated by a durable
  PostgreSQL worker; do not retain Convex snapshot chunking.
- Initialize Better Auth from scratch. Do not load Convex Auth tables or
  SQLite `app_users`, `app_user_permissions`, or `app_sessions` into staging or
  PostgreSQL. Provision a new administrator and approved staff access.
- Treat `productionEntries` and `software_raw` as competing sources requiring
  overlap analysis; do not preserve the current all-or-nothing precedence.
- HR business data is not inside the pricing SQLite database. The checked-in
  project proxies an external Python service backed by
  `recruitment_data.json` and resume files. That requires a separate discovery
  gate before HR can be decommissioned.
- Enable PostgreSQL writes only after read-only production acceptance. Before
  that point, rollback is routing back to the intact read-only legacy sources.
- `docs/adr/0005-unified-postgresql-foundation.md` fixes `apps/web` as the sole
  web shell, `packages/db` as the schema/client boundary, and
  `packages/migration` as tooling that production request handlers cannot
  import.
- `docs/adr/0006-better-auth-redis-runtime.md` keeps PostgreSQL authoritative
  for sessions and capabilities, disables Better Auth cookie session caching
  initially, and limits Redis to disposable acceleration driven by a
  transactional PostgreSQL outbox.

Source availability finding:

- This workspace does not contain `pricing/pricing-data/pricing_app.db`,
  a Pricing data directory, an `mrm-dashboard` Convex local directory, a
  matching Convex Docker volume, or a Convex export.
- Do not start the Pricing application before recovery because `getDb()` would
  create a new empty database at the missing path.
- Recover the complete `pricing-data/` directory and the dashboard's Convex
  export/local deployment data from the original development machine before
  migration implementation.
