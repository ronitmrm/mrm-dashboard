# CSV Imports

## All-or-nothing acceptance

A CSV or spreadsheet upload is one transaction. Every row must pass field,
reference, business-rule, and database validation before any imported changes
are committed. If any row fails, the entire upload is rolled back, including
earlier rows, audit records, generated master codes, and queued refresh work.
The user corrects the reported error and uploads the complete file again.

Dashboard template uploads accept LF, CRLF, and CR line endings, including
quoted multiline cells. A template without data rows is rejected instead of
reporting a successful zero-row import.

All non-empty calendar-date cells must use `DD/MM/YYYY`, with two digits for the
day and month and four digits for the year, and must identify a real calendar
date. Other formats, including ISO dates, month names, two-digit years, and
spreadsheet serial numbers, reject the complete CSV before any imported changes
are applied. Errors identify the CSV row and date column. Downloads use the same
format so valid date fields can be imported again. Stored dates remain canonical
calendar dates; this input rule does not change stored timestamps.

RM Inward kilograms and Work Order piece/kg quantities accept plain numbers and
standard or Indian thousands separators used in downloads, such as `1,015.90`
and `1,23,456.70`. These separators are interpreted only in quantity fields,
not in locations or identifiers. RM Inward validates every received quantity as a
positive number before saving any row and identifies invalid values by CSV row.

## Existing RM locations

Use **Update locations CSV** in RM Inward to update saved receipt locations from
the View Records download. Job Card and receipt date identify the receipts;
all receipts for that Job Card on that date receive the same location. Conflicting
locations for that combination or a row with no matching receipt reject the whole
upload. Received kg is informational in this action and is never written back.
Blank locations leave existing values unchanged. Historical receipts on
cancelled Work Orders can still have their storage location updated.

This action records an audit entry for each changed receipt, creates no receipts,
and does not change stock, receipt dates, Work Orders or the saved machine plan.
Locations are read from current saved receipts on the shop-floor screens, so no
planning recalculation is queued. **Receive RM CSV** continues to record new
receipts using the normal receiving rules.

RM Inward and Work Order record downloads retain the full stored precision of
quantity fields, rather than the rounded numbers used for on-screen display.

## Deduplication

Every CSV or spreadsheet import keeps the first exact business row and skips
later copies before validation or persistence. Differences in real fields—such
as setup number, checklist sequence, quantity, date, or machine—keep rows
distinct.

Uploading the same data again must reuse the existing database identity instead
of creating another record. Existing repository identities continue to govern
planning and operational masters. Auto-coded quality and checklist masters
match by their normalized name or title and reuse only a valid generated code.
Production-output and commercial-register imports use stable import identities.

This rule prevents new duplicates. It does not delete or merge historical
duplicates automatically, because doing so could remove linked operational
history.

The original enquiry-line import file is retained as an uploaded Artifact on
its Import Review. Operational-master, enquiry-register, Commercial Master,
Purchase Order-line, and employee-assignment imports are parse-and-discard:
their parsed business rows persist, but their uploaded workbook or CSV does
not create an Artifact.

## Employee assignment CSV

The downloaded employee-assignment CSV is a current vacancy list, not a blank
template. It includes active combined roles only when every member post is
vacant, and individual approved posts only when they are vacant and are not
members of an active combined role.

`target_type` identifies whether a row addresses one `individual` approved post
or a `combined` role. `target_code` is the approved post code or combined vacancy
code used to resolve that target. These routing values are generated by the
system and should not be edited.

CSV bulk assignment ignores untouched vacancy rows and treats each completed row
as `Appointed` unless a legacy file explicitly supplies `Joined`. Occupied posts
must be vacated manually before assignment; the repository rechecks vacancy at
upload time so an older downloaded file cannot overwrite a later assignment.
The CSV does not include employment-event or last-working-date fields.
