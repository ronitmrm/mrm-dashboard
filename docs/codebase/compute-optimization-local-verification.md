# Dashboard compute optimization: local verification

Verified 2026-09-18 on `perf/compute-optimization`, implementation `941cb43`, against staging baseline `6b4543c`. The local measurements confirm removal of the persistent dashboard request. They do not measure Vercel billing, production CPU, or production database latency.

## Controlled transport comparison

Separate Chromium browsers ran the exact staging and updated React delivery hooks in isolated harnesses over real HTTP; both scoped-provider hooks returned null to select canonical dashboard delivery. The baseline used the original SSE route and Redis subscriber with a disposable local Redis, stubbed authorization and local Redis configuration. Both canonical endpoints returned identical fixture data with a 15 ms server delay. Visibility changed by bringing another browser tab to the foreground; `document.visibilityState` reported `hidden`, without overriding browser APIs.

| Observation | Staging | Updated branch |
| --- | --- | --- |
| Initial canonical reads | 2 (including stream-open revalidation) | 1 |
| Visible steady polling, two intervals | 60,019 / 60,019 ms | 60,019 / 60,018 ms |
| Persistent event streams | 1 | 0 |
| Heartbeats by ~123 seconds | 6 | 0 |
| Additional canonical reads during 65 seconds hidden | 0 | 0 |
| Additional heartbeats during that hidden interval | 3 | 0 |
| Return to overdue visible tab | Immediate read | Immediate read |
| Active refresh request intervals | 1,018–1,020 ms | 1,018–1,019 ms |
| Additional reads during 4 seconds hidden with active refresh | 0 | 0 |

At the end of the idle visible/hidden portion, the staging stream had remained open for at least **188 seconds** and was still open; this is an observed elapsed duration, not a completed stream lifetime. The updated branch held no stream open. This demonstrates removal of the persistent request, **not CPU time or billable instance duration**. Existing 60-second polling and version-based payload savings are preserved behavior, not newly introduced speedups.

## Authenticated production build

The enabled Next.js production build ran against disposable PostgreSQL and Redis. An authenticated administrator opened the production dashboard with a real worker-generated, empty-business-data model.

- Visible steady request interval: **60,044 ms**. Both initial and steady reads returned HTTP 200 and finished in **36 ms** and **27 ms** respectively (browser-observed request lifetime).
- **Zero additional canonical-state or dashboard-event requests during 65 seconds in a real background tab**. Returning to the foreground triggered one canonical read immediately. No dashboard-event stream was initiated by the dashboard.
- Clicking **Recalculate Planning** queued a real durable job. Canonical request intervals were **1,022–1,025 ms**. A 4-second hidden interval added zero reads. Running the real refresh worker completed the job, advanced the model from version 1 to 2, and the foreground dashboard returned to its settled state.
- DOM text snapshots retained dashboard KPIs and the empty table at each check and queued-refresh checkpoint; a final screenshot confirmed the settled view. This does not validate a populated production dashboard. No uncaught browser errors were captured by the `pageerror` listener; console errors were not exhaustively collected. Transient failure retention was covered by the earlier hook fixture; this full-app capture did not inject a failure.
- Separate sequential authenticated endpoint sample: one full response **14,814 bytes / 18.2 ms**, followed by 29 unchanged-version responses, each **246 bytes** (`notModified: true`, `dashboard: null`). Unchanged response latency: **p50 14.3 ms, p95 16.2 ms**. Byte counts are decoded JSON body sizes, not compressed wire bytes; percentiles use nearest-rank over the 29 warm unchanged reads. This was not an A/B database benchmark.
- Anonymous canonical request: **401**. Explicit probe of retired `/api/dashboard-events`: **404**, finite JSON response. The latter request was made by the verification script, not the dashboard.

The app's timed polling phases preceded the separate endpoint sample; the 30 manual reads and explicit retired-route probe are excluded from polling counts. Existing test, lint, typecheck and build results remain recorded in [the checklist](compute-optimization-checklist.html); the dashboard-enabled production build also passed during this verification.

## Evidence and limits

- Disposable PostgreSQL 16 and Redis; real temporary administrator, real authorization, and a read model generated by the durable refresh worker. No live databases or deployment touched.
- The initial build had pre-rendered the dashboard-disabled redirect. Rebuilding with `PRODUCTION_MODULE_ENABLED=true` enabled the actual dashboard. Production builds must receive the intended module setting at build time as well as runtime.
- Timing probes are local, single-browser measurements with empty business tables. They establish transport behavior, not throughput or production-load performance.
- A/B evidence: `/tmp/mrm-perf-local-results.json`; authenticated-app evidence: `/tmp/mrm-perf-full-results.json`; screenshot: `/tmp/mrm-perf-full-dashboard.png`. Temporary harnesses: `/tmp/mrm-perf-ab-server.mjs`, `/tmp/mrm-perf-measure.mjs`, `/tmp/mrm-perf-full-measure.mjs`. These paths are local scratch artifacts, not portable repository dependencies.
- Temporary browsers, servers and disposable containers were stopped; local test credentials were deleted after verification.
- Production acceptance remains: deploy, confirm retired-route invocations cease, and compare Fluid usage over comparable traffic windows. Local request lifetime cannot establish a specific percentage or dollar saving for shared platform instances.
